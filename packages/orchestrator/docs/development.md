# 🛠️ Development

## 📋 Prerequisites

Tool versions are pinned in the workspace root's [`mise.toml`](../../../mise.toml). Install
[mise](https://mise.jdx.dev), then let it provision Bun and Node, and install the workspace:

```sh
mise install      # installs the pinned Bun and Node
bun install       # from the workspace root
```

The `docker` provisioner additionally needs a docker launcher
([@ryph/launcher](../../launcher/README.md)) at `RYPH_LAUNCHER_URL`, which holds the docker CLI and
socket; the `kubernetes` provisioner needs a pod whose service account may manage Jobs in the runs
namespace, or `kubectl proxy` and `RYPH_K8S_API_URL` from outside one — see
[kubernetes.md](kubernetes.md); the default `manual` provisioner needs nothing but Bun.

## ⚡ Tasks

Defined in [`package.json`](../package.json) (fmt and lint are the workspace root's `bun run fmt`
and `bun run lint`):

| Task                  | What it does                                                                       |
| --------------------- | ---------------------------------------------------------------------------------- |
| `bun run ci`          | the package's gate — typecheck, architecture guard, tests; run this before pushing |
| `bun run dev`         | runs the orchestrator (reads the env knobs below)                                  |
| `bun run test`        | runs the test suite in `tests/`                                                    |
| `bun run check`       | type-checks `src/`, `scripts/`, and `tests/` (`tsgo`) without running anything     |
| `bun run guard`       | architecture guard (enforces the import/dependency fence)                          |
| `bun run db:push`     | applies `schema.ts` straight to the database — local dev, no migration files       |
| `bun run db:generate` | generates SQL migrations from the schema into `./drizzle` (cutting a release)      |
| `bun run db:migrate`  | applies generated migrations (deployments)                                         |
| `bun run db:studio`   | opens the database in a browser                                                    |

## 🗄️ Database

Persistence is [drizzle](https://orm.drizzle.team/) on PostgreSQL — embedded via PGlite, so the
default local setup still needs no database server.
[`src/adapters/store/db/schema.ts`](../src/adapters/store/db/schema.ts) is the source of truth;
everything a UI sorts or filters on is a real indexed column, and reads go through the relational
`db.query.*` API so swapping the backend stays a schema-and-driver edit. The workflow:

- **Local dev & tests: `db:push`.** The schema is pushed straight onto the database; there are no
  migration files to write or apply while the schema is still moving. Tests push the schema
  programmatically onto a fresh `:memory:` database per test ([`tests/db.ts`](../tests/db.ts)), so
  they exercise the same push path as local dev.
- **Deploys: generated migrations.** `db:generate` at release time, `db:migrate` on the deployment.

This package's [`drizzle.config.ts`](../drizzle.config.ts) covers **its own tables only** — the
standalone deployment's database. The default local deployment pushes every mounted module's schema
(this package's, auth's, model-proxy's) from [@ryph/host](../../host/README.md)'s combined config in
one shot.

> **Postgres, three ways.** `RYPH_DB` is a URL: `pglite:<path>` (embedded, on disk),
> `pglite:memory://` (throwaway) or `postgres://…`. All three are real PostgreSQL 17 and the store
> adapters are identical on all of them — see [@ryph/db](../../db/src/url.ts). Atomic
> multi-statement writes are plain `db.transaction()`; the `db.batch([...])` that libsql's
> connection-hopping forced is gone.

### Egress is enforced on two backends, and cooperative on the rest

Every run on every backend is handed the proxy and its allowlist. What differs is whether a run can
go _around_ them, and that is a property of the network the run sits on rather than of anything ryph
hands it.

| Backend      | Enforced?                      | What makes it so                                                                                                                                                                                          |
| ------------ | ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `kubernetes` | yes                            | A NetworkPolicy on `ryph-runs` permits the proxy and nothing else                                                                                                                                         |
| `docker`     | with `RYPH_DOCKER_RUN_NETWORK` | The run joins an `--internal` network alone and reaches ryph through the run gate's fixed route list. Without it the run keeps its default route, warned once per process as `docker.egress_not_enforced` |
| `manual`     | no                             | The runner is started by hand, on whatever network its operator chose                                                                                                                                     |

Cooperative is not nothing: the runner routes its own setup steps through the proxy, so the
allowlist still shapes what an ordinary run installs. It is simply not a boundary an adversarial
process respects — and the point of the table is that one setting should not read as enforcement on
the backends where it is a preference.

### Model access, and the two master keys

Model access reaches a standalone [@ryph/model-proxy](../../model-proxy/README.md) over its internal
surface (`adapters/model_access/http.ts`), behind the same `ModelAccess` port the single-process
[@ryph/host](../../host/README.md) fills with an in-process issuer. Two knobs turn it on —
`RYPH_MODEL_PROXY_CONTROL_URL` and `RYPH_MODEL_PROXY_TOKEN` — and it is gated on the URL: a token
alone describes no peer to dial.

The platform's background model (the one an admin sets under Instance → Platform) is reached the way
memory reaches it: `RYPH_PLATFORM_TOKEN` mints a platform credential on the proxy's control listener
(consumer `titles`), and it is spent on the data listener at `RYPH_MODEL_PROXY_DATA_URL`
(`adapters/platform_model/proxy.ts`). The control plane never holds a provider key. It names tasks
nobody titled; without it, or when the call fails or is slow, a task keeps the first line of its
instructions.

Deliberately absent here: `RYPH_MODEL_PROXY_URL` (what an agent _container_ dials) and
`RYPH_VIRTUAL_KEY_TTL_MS`. Both belong to the proxy, which builds the container's env itself because
it is the one that knows how containers reach it.

Tool access is the same link one credential class over: `RYPH_MCP_GATEWAY_CONTROL_URL` and
`RYPH_MCP_GATEWAY_TOKEN` reach a standalone [@ryph/mcp-gateway](../../mcp-gateway/README.md)'s
internal surface (`adapters/tool_access/http.ts`) behind the `ToolAccess` port.
`RYPH_MCP_GATEWAY_URL` (what a container dials) and `RYPH_MCP_KEY` are the gateway's, for the same
reason.

`RYPH_SECRETS_KEY` is likewise **not** read here any more. It seals provider secrets and lives with
the proxy: a compromised control plane should not be able to open a provider key it has no reason to
touch.

### This process is the control plane, and the control plane is orchestrator + auth

[@ryph/auth](../../auth/README.md) is **mounted here**, not dialed. Its tables already live in this
database (see its `schema.ts`), the app's login round trip and the user surface it gates are the
same origin, and a separate process would only add a second holder of the signing key. So
`bun run db:push` provisions both schemas, and this process serves `/v1/auth/*` and
`/.well-known/jwks.json` alongside everything else. The sibling services — historian, model-proxy —
point their `RYPH_AUTH_URL` at **this** process.

`RYPH_AUTH_URL` still exists here and now means the opposite of what it used to: set it to verify
against some other issuer's JWKS instead of the mounted one. Leave it unset.

### Health and drain

`GET /healthz` and `GET /readyz`, from [@ryph/service](../../service/README.md), are mounted
unauthenticated — a load balancer carries no bearer. Liveness asks nothing; readiness reads one row
and answers 503 the instant a drain begins. SIGTERM drains in order (unready → listener → reaper and
connection) on a deadline, because `serve()`'s `shutdown()` would otherwise wait on in-flight work
forever.

## ▶️ Running a real run

The manual provisioner is the fastest way to watch the whole loop without docker: it launches
nothing and **prints the exact env a runner needs**, so you can hand-start one.

1. **Boot the orchestrator** on a throwaway in-process database:

   ```sh
   RYPH_PROXY_SECRET=$(openssl rand -hex 32) RYPH_DB=pglite:memory:// RYPH_AUTH=off bun run dev
   ```

   (`RYPH_AUTH=off` skips the login dance while poking at it by hand; leave it on for anything real,
   and claim the owner via `POST /v1/auth/users` with the setup token from the log.)

2. **Create an agent, then a task:**

   ```sh
   curl -s localhost:7411/v1/agents -d '{"name":"Ada","email":"ada@ryph.dev","harnessKind":"echo"}'
   curl -s localhost:7411/v1/tasks -d '{"agentId":"<id>","spec":{"title":"…","instructions":"…"},"repo":{"url":"…","ref":"main"}}'
   ```

   The orchestrator mints the run and — because the provisioner is `manual` — logs the container env
   (`RYPH_ORCHESTRATOR_URL`, `RYPH_RUN_ID`, `RYPH_BOOTSTRAP_TOKEN`, …).

3. **Hand-start a runner** with that env, pointed at the same machine. It fetches its spec
   (`GET /v1/runs/:id/spec`), heartbeats, and POSTs its result — exactly what a real container does.

4. **Watch it:** `GET /v1/tasks/:id` shows the run's state and its event trail.

Swapping `RYPH_PROVISIONER=docker` (with `RYPH_AGENT_IMAGE` set) makes step 3 automatic: a docker
launcher ([@ryph/launcher](../../launcher/README.md)) starts the pre-baked
[agent-container image](../../../images/README.md). This process runs no docker itself, so it needs
one to talk to: start one with `bun run dev` in `packages/launcher` and point `RYPH_LAUNCHER_URL`
and `RYPH_LAUNCHER_TOKEN` at it. Without them a docker control plane refuses to boot.

does with each port; this doc is only how to run and change it.
