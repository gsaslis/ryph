# 🧩 Skills

How a run gets the playbooks ryph writes about its own configuration files, the ones an org keeps in
its skills repo, and the ones each checked-out repo commits, in the
[Agent Skills](https://agentskills.io/specification) format coding harnesses read: a directory with
a `SKILL.md` (frontmatter naming it and saying when to read it, then a Markdown body) and whatever
references it carries. Only each skill's name and description are listed to the model; it reads the
rest when a task calls for it, so a run can carry several without its prompt growing.

## 📚 The ryph skills catalogue

`packages/orchestrator/skills/`, one directory per skill:

| Skill                  | What it documents                                                                                                  |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `ryph-artifact-design` | Writing a single-file HTML artifact that renders under the content route's sandbox, and publishing and updating it |
| `ryph-checks`          | `.ryph/checks.yml`: the format, that the base judges, the pod model, and running checks from a run                 |
| `ryph-environment`     | `.ryph/Dockerfile`, `setup.yml`, `services.yml` and `environment.md`, and how to verify an environment             |

It ships with the orchestrator, not the harness image, because the formats it documents are parsed
here and in the forge: a change to what `checks.yml` means changes the skill in the same commit, and
a run is always told the rules of the control plane that will judge it.

- **Loading.** `adapters/skill_catalogue/directory.ts` reads and validates the directory once, at
  boot, through `import.meta.url`, so the same path works from source, from the control-plane image
  (its Dockerfile copies `skills/`, and `.dockerignore` re-includes it) and from the `ryph` binary
  (its compile step `--include`s it and refuses to build without it). Any problem fails the boot,
  naming every file and issue: a warning that would only drop a field from another source is a
  failure for platform-authored content. Every file is read as not executable, whatever its mode, so
  the digest is the same from source and from the binary's embedded filesystem.
- **Names.** Every catalogue skill's name starts with `ryph-`, and only the catalogue may use that
  prefix.
- **Storage.** Both composition roots upsert every catalogue bundle into `skill_bundles` at boot
  (`insert … on conflict do nothing`). A run frozen before a deploy, one that waited out an
  environment build across it, still fetches the version it was frozen with. Bundles are never
  deleted.
- **Kept true by test.** `tests/skill_catalogue_test.ts` loads the directory through the real
  adapter, runs every fenced block whose first line is `# .ryph/checks.yml` or
  `# .ryph/services.yml` through the parser that reads that file (and each service through the
  service catalogue), checks the limits, names and image the text states against the constants that
  enforce them, and holds the catalogue under half of each listing cap. The runner checks the
  `# .ryph/setup.yml` blocks with its own parser
  (`packages/runner/tests/skill_catalogue_examples_test.ts`).

To write a skill: a directory named for the skill, a `SKILL.md` whose description says when to read
it in the words a task would use ("Read before creating or changing …"), a body under a few hundred
lines with the full field reference in `references/`, and every example of a ryph file tagged with
its path as its first line so the tests parse it.

## 📂 Working-repo skills and Claude Code compatibility

When working-repo skills are enabled, the runner reads committed `.agents/skills/<name>/SKILL.md`
and `.claude/skills/<name>/SKILL.md` from each checkout's base commit, before setup. No copying or
setup step is needed. Both directories use the same validation rules and share the per-repo limits;
adding a second directory does not double the allowance. Uncommitted files and skills generated by
setup are not loaded.

Frozen catalogue and org skills win first, then repositories in checkout order. Within a repo,
candidates are considered in name order, with `.agents/skills` winning equal names. A committed
`.agents` skill directory or link shadows a same-name `.claude` skill even if the preferred copy is
invalid; there is no fallback or file merging. The collision is reported in the run's skill drops
rather than silently ignored. Both copies count toward the shared directory cap. Org skills repo
syncing still reads only `.agents/skills`; the additional directory applies to working checkouts.

`.claude/agents/*.md` is deliberately **not imported as subagent presets**. Those definitions carry
Claude Code-specific model, tool and permission semantics that Ryph cannot faithfully apply. Ryph
subagents receive an explicit task and an `explore` or `work` mode through `ryph__subagent_start`; a
Markdown definition must not silently grant tools or change permissions. Move reusable instructions
into a `SKILL.md` in either supported directory, and include the relevant instructions in a
subagent's task when delegating. This does not prevent an agent from reading a repository file
explicitly; it means these files are not automatically registered as presets.

See [the runner's discovery and materialization rules](../../runner/docs/harnesses.md#-skills).

## 📏 What a valid skill is

`core/skills.ts` `judgeSkill`, with `helpers/skill_file.ts` splitting and parsing the frontmatter.
The runner restates what it needs of the same rules (`packages/runner/src/helpers/skills.ts`).

| Rule                                                                                                                                                           | On failure    |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------- |
| `SKILL.md` is a regular file of at most 64 KiB, valid UTF-8                                                                                                    | skill dropped |
| The file starts with a line `---`, and a later line `---` closes the frontmatter, which parses to a mapping                                                    | skill dropped |
| `name`: 1–64 chars of `^[a-z0-9]+(-[a-z0-9]+)*$`, equal to the directory name; `ryph-` only in the catalogue                                                   | skill dropped |
| `description`: non-empty after trimming, at most 1024 chars, no control characters but `\n` and `\t`, no unpaired surrogate                                    | skill dropped |
| `disable-model-invocation: true` (pi would load it and hide it from the model)                                                                                 | skill dropped |
| `license` ≤ 200 chars, `compatibility` 1–500, `metadata` ≤ 32 string keys to strings ≤ 1024, `allowed-tools` ≤ 1024; none holds a NUL or an unpaired surrogate | field dropped |
| Every other file is regular (no symlinks or submodules), each path segment `^[A-Za-z0-9._-]{1,128}$`, at most 8 deep                                           | file skipped  |
| At most 64 files and 512 KiB per skill                                                                                                                         | skill dropped |
| No path twice, and no file that is also the directory of another (`x` and `x/y`), which a tree built without git's fsck can hold                               | skill dropped |

Every drop and skip carries a warning naming the path. `allowed-tools` is carried and never
enforced, by ryph or by pi.

The **digest** is over the source bytes:
`"sha256:" + hex(sha256(for each file sorted by path: path 0x00 ("x"|"-") 0x00 length 0x00 bytes))`.
Two skills with the same files have the same digest wherever they came from.

## 🎨 Presentation

How the skills page shows a skill: `core/skill_presentation.ts` `skillPresentation`, run by
`judgeSkill`, so every valid skill carries `presentation`, its text, and `icons` (each null when it
sets nothing). The source is OpenAI Codex's `agents/openai.yaml`, read the way Codex reads it:

```yaml
interface:
  display_name: "Release" # whitespace collapsed; over 64 chars, left out
  short_description: "Cut a release." # over 1024 chars, left out
  icon_small: "./assets/small.svg" # relative, under assets/, no '..'; at most 16 KiB
  icon_large: "./assets/large.png" # at most 64 KiB
  brand_color: "#3B82F6" # exactly #RRGGBB
  default_prompt: "Cut a release." # over 1024 chars, left out
policy:
  allow_implicit_invocation: true # true unless false; shown, not enforced
```

`openai.yaml` is read, or `openai.yml` when there is no `.yaml` (Codex reads only the first, but
skills in the wild ship the second), with the `agents` directory matched in any case. The
frontmatter's `metadata` adds `author` and `version`, and `short-description` when the file has no
`short_description`. An icon must be a file of the skill under `assets/` whose path segments hold to
the skill file grammar (`pathRefusal`), at most 16 KiB for `icon_small` and 64 KiB for `icon_large`,
and a PNG, JPEG, WebP or SVG by its bytes, never its name (an SVG is UTF-8 whose first element is
`<svg`; a doctype with an internal subset is refused). Icons are `{ mime, data }` with `data`
base64; render them as an image, never inline the SVG markup. A warning names an icon path only once
it passed that grammar, and a YAML parser message is made storable first, since warnings are stored
in jsonb.

A missing file is no presentation. A file that does not parse, or a field that does not fit, is left
out with a warning on the sync (and fails the catalogue's load, as every warning does); the skill
stays. Both ryph catalogue skills ship an `agents/openai.yaml` and an SVG icon under `assets/`.

Where it lives:

- **Text** in `skill_sync_entries.presentation` (displayName, shortDescription, brandColor,
  defaultPrompt, implicitInvocation, author, version). `currentOrg()` and `orgState()` read it, and
  a run start reads `currentOrg()`, so it never carries an icon.
- **Icons** once per digest in `skill_bundles.icons`, `{ small, large }`, written with the bundle. A
  later sync of the same content updates them only when it judged them differently (icon rules can
  change under the same bytes). The absent one is stored as null, never as a copy of the other. Read
  apart through `SkillStore.iconsOf(digests)`, one query of the icons column alone.
- **Catalogue skills** hold both in memory.

The API folds the icons into `presentation` as `iconSmall` and `iconLarge` (`presentationView`),
null when the skill sets neither text nor icon. `GET /v1/skills` carries `iconSmall` only: the small
icon, or the large one when there is none and it fits 16 KiB; `iconLarge` is null. A skill's own
page (`/v1/skills/catalogue/:name`, `/v1/skills/org/:name`) carries both, each standing in for the
other when only one is set.

## 🧮 What a run is given

In `startTask`, before anything is written, `resolveRunSkills` freezes the run's list onto
`runs.skills` (`RunSkills`: each skill's name, description, source and digest; the org repo version
the org skills came from; whether the runner may add the checked-out repos' own; the listing budget
left for them). The settings and the org repo's current version are read live at each task start
(`SkillStore.settings`, `currentOrg`), never cached, so a sync or a toggle is in effect for the next
run on every replica.

1. A harness that reads no skills (`core/harness_tools.ts` `supportsSkills`: pi yes, echo no) gets
   nothing frozen: `skills` is null, and nothing is read.
2. Every catalogue skill, in name order, minus any an admin turned off, minus any the agent's
   `skillPolicy` turned off unless the task's purpose pins it.
3. Then the org repo's current version, unless the agent turned the repo off: its skills in name
   order, minus any the agent turned off. A `ryph-` name is dropped as reserved; the sync refused
   those already, and precedence is decided here.
4. A name already taken is dropped as a collision, naming the source that holds it: the catalogue
   wins over the org repo, and both win over the working repos the runner adds.
5. The caps: at most 32 skills (`MAX_LISTED_SKILLS`) and 16 KiB of names and descriptions
   (`MAX_LISTING_BYTES`) listed per run, pinned skills admitted first, then the catalogue, then the
   org repo. pi has no limit of its own, and the listing rides every turn's system prompt.
6. `workingRepos` is the deployment's switch and the agent's together; the runner reads the repos'
   own skills only when both are on ([the runner's side](../../runner/docs/harnesses.md#-skills)).

The frozen `org` names the version (repo, commit, sync, when it was synced) only when it gave the
run at least one skill. **While the latest read of the org repo is failing**, runs keep the last
good version; such a run's `org.stale` is true and its trail gets a `skills.stale` event naming the
repo, the commit, when it was synced and the failure (`describeStale`).

Drops are written as one `skills.dropped` run event at creation, and the runner's report adds one
for what it could not load; both are worded by `describeDrops`, so a reason reads the same whoever
saw it. Turning a skill off is a decision, not a drop, and writes nothing.

**The setup task.** "Set up this repo's environment" (`purpose: "environment-setup"`) pins
`ryph-environment` over the agent's own switch, never over an admin's: the route refuses a setup
task that would not hold it (an admin turned it off, no catalogue, a harness without skills). Its
platform-authored instruction names the skill, leaves every format rule to it, and carries only the
task: what to read, which files to write, the workspace split, the build loop and when to stop. A
run whose runner dropped the skill is told to stop and say so rather than write `.ryph/` from
memory.

**Artifacts.** A run whose agent may publish artifacts (`canPublishArtifacts`) is pinned to
`ryph-artifact-design` the same way, over the agent's own switch and never over an admin's, and a
run whose agent may not is never given it: it is about a tool that run does not hold. Nothing is
refused when an admin turned it off: the agent can still publish, it only writes the page without
the guidance (`core/artifacts.ts` `ARTIFACT_SKILL`, [artifacts](artifacts.md)).

**Deployment features.** Catalogue skills are listed whatever the operator turned on. Each says what
changes when its feature is off (`ryph-checks` for checks, `ryph-environment` for environments and
services) and which tool tells the agent which is the case.

## ⚙️ Settings and the agent's policy

**The deployment's settings** are one `skill_settings` row (`SkillSettings`), read as the defaults
while it does not exist: every catalogue skill on, working-repo skills allowed, no org skills repo.
The admin's switches (`disabledCatalogue`, `workingRepoSkills`) are written apart from the org
repo's columns (`SkillStore.putToggles`), so flipping one never writes back a version pointer a sync
moved in between. The org skills repo is one connected repo and an optional branch
(`SkillStore.setOrgRepo`); naming another repo or branch clears the current version and the last
answer, so a version of the old one is never what runs get.

**The agent's `skillPolicy`** (`agents.skill_policy`, `SkillPolicy`) narrows only: lists name what
is off, so a skill added later reaches the agent without an edit. It points at no secret and cannot
exceed the deployment, so `agents:write` is its whole gate. The handler refuses a catalogue name the
catalogue does not ship (one the stored policy already held is dropped instead, so a release that
removes a skill does not fail every edit), refuses any non-default policy on a harness that reads no
skills, and stores a policy equal to the defaults as null.

**Versions.** Each read of the org repo that changed something is a `skill_syncs` row: a new tree
(with its skills in `skill_sync_entries`, their files in `skill_bundles`) or a failure. A read that
found the tree runs already get, judged by the same `SKILL_RULES_VERSION`, is no row and moves only
the last answer (`checkedAt`, `checkedCommit`). A failure identical to the latest read of the same
repo and branch counts as a repeat of it. `SkillStore.recordSync` makes that write in one
transaction under `SKILLS_SYNC_TX_LOCK` (`8_100_008`), and moves the current version only while the
settings still name the repo and branch the read started with and no read that started later has
answered. Syncs are not serialized, so start order is the order they are judged by: every answer
records when its read started (`org_checked_started_at`), a standing failure included, and only
moves it forward. So a slow tree cannot land over a newer read that found the branch gone. A slow
read of a repo or branch an admin has since swapped out, or one a later answer overtook, is kept as
a `superseded` row, a failure included, and moves neither the version nor the last answer, nor marks
runs stale. An unchanged answer counts only while runs still get the tree the read named to the
forge: when a read that started earlier landed another tree meanwhile (a push and its revert close
together), the answer is `behind`, records nothing, and the sync reads the whole tree again. A
skill's versions are the `synced` rows of the repo and the branch the current version was read from.
While the newest failure is newer than both the current version and the last answer, runs stay on
the last good version, marked stale. An archived skills repo gives runs no org skills until an admin
picks a repo again.

## 🔄 Syncing the org skills repo

`core/skills_sync.ts` `syncOrgSkills` is the one read, whatever started it:

| Trigger     | When                                                                                        | Who waits                                                        |
| ----------- | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `connect`   | `PUT /v1/skills/org-repo`                                                                   | The request, which answers with what the read did                |
| `push`      | A `branch.updated` for the skills repo, on the branch the settings read (null: the default) | Nobody: started after the environments hook, never awaited       |
| `manual`    | `POST /v1/skills/org-repo/sync` (Sync now)                                                  | The request                                                      |
| `reconcile` | At boot and hourly (`RYPH_SKILLS_RECONCILE_INTERVAL_MS`)                                    | Nobody; one replica, under `LOCK_SKILLS_RECONCILE` (`8_100_009`) |

Both forges send `branch.updated` for a repo's default branch only, so a non-default branch is
synced by Sync now and the reconcile. The reconcile's leader lock and the store's write lock
(`8_100_008`) must stay different keys: the reconcile holds its lock on one session while its sync's
write takes the other on a pooled connection, and one shared key would wait on itself. The host
composition is one process and has no locks; its reconcile is an interval with an in-flight flag and
a boot kick.

**The read.** The forge's `POST /v1/service/skills-tree` (`ForgeSkills.readSkillsTree`, kept off
`Forge` like `ForgeChecks`) answers every file under `.agents/skills/` at the branch's tip: path,
git mode and base64 bytes, read through one binary-safe `git cat-file --batch`, bounded at 2,000
entries and 8 MiB from the tree listing before any content is read, and the listing itself at 2.5
MiB. The branch is strictly refreshed; a failed refresh is `unavailable`. The sync passes the
current version's tree id as `knownTree` when that version was judged by the running
`SKILL_RULES_VERSION`, and an unchanged directory costs no content. The request has the forge reads'
120 s deadline, so a connect against a cache that has never seen the repo is not cut off by the
generic one.

**Judging.** Every directory directly under `.agents/skills/` is one skill, judged by the rules
above with `ryph-` reserved; files directly in the root are passed over. At most 100 directories are
judged, by name, with a warning naming the cut, and at most 100 warnings are kept, the rest counted
in one more. A sync succeeds whenever the tree could be read: invalid skills are dropped one by one
and the rest are the version. No `.agents/skills/` at all is a version with no skills.

**What it records.** The store's write decides (see Versions above): a new version, `up-to-date`, a
failure (`unavailable`, `missing-ref` for a deleted branch, `invalid` for a tree over the forge's
bounds, a submodule at `.agents/skills`, or a ref or repo it refuses outright, `error` for anything
unexpected, a timeout included), or `superseded` when the settings moved to another repo or branch
while the read ran, or a read that started later answered first. With no forge wired, every read
fails as `unavailable`; the noop forge says the same, since it reads no repo.

## 🌐 The skills API

Reading takes `skills:read` (member), every write `skills:manage` (operator), like `tools:read` and
`tools:manage` for MCP servers.

| Route                                 | Does                                                                                                                                                                                                                                                                                                                                   |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /v1/skills`                      | The page and the agent editor in one answer: `catalogue` (each skill with `enabled` and `presentation`), `org` (the repo, `branch`, `effectiveBranch`, `current` with its commit, skills (each with `presentation`) and warnings, `checkedAt`, `stale`, `lastFailure`, `archived`) or null, `workingRepoSkills`, `limits`, `updatedBy` |
| `GET /v1/skills/catalogue/:name`      | A catalogue skill and its files: text inline when it is UTF-8 with no NUL, otherwise size only                                                                                                                                                                                                                                         |
| `GET /v1/skills/org/:name`            | A skill of the current org version: its files, its warnings, and `versions` of the current branch newest first, each with the sync and commit it first and last appeared in                                                                                                                                                            |
| `GET /v1/skills/bundles/:digest`      | One version's files, catalogue or org                                                                                                                                                                                                                                                                                                  |
| `GET /v1/skills/syncs?cursor=&limit=` | Sync history across repos, newest first by finish time; `cursor` is the previous page's `nextCursor`, and one this surface did not issue is a 400                                                                                                                                                                                      |
| `PUT /v1/skills/settings`             | `{ disabledCatalogue, workingRepoSkills }`; names held to the shipped catalogue. Answers the overview                                                                                                                                                                                                                                  |
| `PUT /v1/skills/org-repo`             | `{ connectedRepoId, branch }`; a live connected repo, `branch` null for its default. Runs a `connect` sync and answers the overview with `sync: { outcome, sync }`                                                                                                                                                                     |
| `DELETE /v1/skills/org-repo`          | Disconnects; history and bundles stay. Answers the overview                                                                                                                                                                                                                                                                            |
| `POST /v1/skills/org-repo/sync`       | Sync now: 409 with no repo connected or an archived one; otherwise the overview with `sync: { outcome, sync }`, `outcome` one of `synced`, `up-to-date`, `failed`, `superseded`                                                                                                                                                        |

## 🚚 Delivery

| Route                             | Does                                                                                                                                                                                                                                                                                                                                                                                                                             |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /v1/runs/:id/spec`           | Carries `skills`: the frozen list, whether the repos' own may be added, and the budget, without the org provenance. Null for a run with none                                                                                                                                                                                                                                                                                     |
| `GET /v1/runs/:id/skills/:digest` | One bundle's files (`{ path, executable, content /* base64 */ }`), from the catalogue this process booted with, else the store. 404 for a digest the run was not frozen with, 409 once the run is terminal                                                                                                                                                                                                                       |
| `POST /v1/runs/:id/skills/report` | The runner's half of the trail: where it wrote the run's skills (`skills.root`), the working-repo skills it loaded (`skills.repo`) and the skills it could not give the agent (`skills.dropped`). Names and repo paths are held to what the run holds: no repo skill when working-repo skills are off, no reserved name loaded, nothing loaded past the budget, and one report per run (a second is refused whole with 409). 204 |

All three are run-token authenticated like every runner route. The content travels separately from
the spec so the boot fetch stays small. What the runner does with a bundle (checks it against its
digest, writes it after setup, hands the harness one `--skill` path per skill) is
[the runner's harnesses doc](../../runner/docs/harnesses.md#-skills).

## 🛡️ Trust

Catalogue skills are ryph's own content, changed through review and validated at boot and in CI. Org
skills are whatever anyone who can push to the skills repo's synced branch writes: in effect an
org-wide prompt that repo's writers edit, so branch protection there is the operator's real control.
The platform reads that content and never executes it, and connecting a repo publishes its
`.agents/skills/` to every member and, by default, every run. Skills are instructions, never
permissions: a skill's scripts run as the agent, in the run's sandbox, under the run's egress policy
and tool scope, exactly as a command the agent typed. No new host and no new credential: content
reaches the container from the orchestrator over the runner's existing token, and a container can
fetch only the digests its own run was frozen with. The listing cannot break out of pi's prompt: pi
XML-escapes every field, and the platform bounds the description's length and characters and
normalizes the frontmatter pi parses.

Working-repo skills are on by default, and they are the repos' own content: anyone who can commit to
a repo the run checks out, the author of the change request a run checks out included, can put a
listed skill in front of that run's agent, the standing that repo's `AGENTS.md` already has. The
runner reads them from git objects at the clone's base commit, never the worktree, and writes them
only after setup, so a setup step cannot add or rewrite one; an adopted checkout trusts the image
build that made its objects. Each is written under `repo/<checkout path>/` in the run's skills
directory, so the location the agent is shown says which repo wrote it. An admin turns them off for
the deployment (`workingRepoSkills`), an agent for itself (`skillPolicy.workingRepos`).
